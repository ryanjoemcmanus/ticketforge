# Deployment runbook

TicketForge is deployment-ready, but this repository does not provision or publish anything by itself. `render.yaml` is an inert blueprint until a repository owner imports it into Render.

## Release gate

Run these checks before every deployment:

```bash
./mvnw verify
docker build -t ticketforge:release .
docker run --rm ticketforge:release java -version
```

The verification suite starts an isolated PostgreSQL 17 container, applies every Flyway migration, exercises the REST workflow, and runs the synchronized seat-race test.

## Required production configuration

Copy `.env.example` to `.env` for a production-like local rehearsal. Replace every placeholder. At minimum, configure:

- `DB_URL`, `DB_USERNAME`, and `DB_PASSWORD`
- a random `JWT_SECRET` of at least 32 bytes
- the externally reachable `APP_URL`
- one-time `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD`

Keep `DEMO_DATA=false` and `EXPOSE_DEVELOPMENT_TOKENS=false`. Once the first administrator exists, remove the two bootstrap variables from the runtime environment.

Start the hardened local stack with:

```bash
docker compose --env-file .env -f compose.production.yml up --build
```

## Render blueprint (not deployed)

The root `render.yaml` describes one Docker web service and one managed PostgreSQL database. If you later choose Render:

1. Push the private repository to your Git host.
2. In Render, create a Blueprint from the repository. This is the point where infrastructure would be created.
3. For `DB_URL`, enter the database's internal connection details in JDBC form: `jdbc:postgresql://HOST:PORT/ticketforge`.
4. Provide `APP_URL` and one-time bootstrap administrator values when prompted.
5. Leave payments on `mock` and notifications on `log` for the first private deployment.
6. Confirm `/actuator/health/readiness` is healthy before enabling external traffic.

No deploy command, cloud account, custom domain, or public endpoint has been created as part of this project preparation.

## Email delivery

Local mode records notifications in structured application logs. To use an SMTP test inbox or production provider, configure:

```text
NOTIFICATION_PROVIDER=smtp
MAIL_FROM=noreply@example.com
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=...
SMTP_PASSWORD=...
SMTP_AUTH=true
SMTP_STARTTLS=true
MAIL_HEALTH_ENABLED=true
```

Connection, read, and write timeouts are bounded at five seconds. Notification handling runs after the database transaction commits, and a delivery outage does not roll back a valid order.

## Stripe test mode

TicketForge rejects live Stripe keys by design. To run a private Stripe sandbox:

```text
PAYMENT_PROVIDER=stripe
PAYMENT_CURRENCY=usd
STRIPE_SECRET_KEY=sk_test_...
```

The browser must supply a Stripe PaymentMethod ID generated by Stripe.js rather than raw card details. The server creates and confirms a PaymentIntent and uses that PaymentIntent reference for refunds. Signed Stripe webhook events are verified, deduplicated, and retained for audit/reconciliation. Before accepting real payments, add an outbox-backed recovery worker for provider events that require an order-state transition.

## Operations checklist

- TLS terminates at the hosting ingress.
- PostgreSQL backups and point-in-time recovery are enabled.
- Database access is private-network only.
- Secrets live in the hosting provider's secret store, never Git.
- Readiness checks use `/actuator/health/readiness`.
- Logs are collected without verification tokens, passwords, payment methods, or JWTs.
- Alerting covers elevated 5xx rates, database pool exhaustion, and failed notifications.
- A restore drill is completed before accepting real purchases.
